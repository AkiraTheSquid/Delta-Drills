DELTA DRILLS — LOCAL VS DEPLOYED STORAGE ARCHITECTURE
======================================================

OVERVIEW
--------
The app has two storage modes depending on where it runs:

  LOCAL (main branch, localhost)
    - Practice state: localStorage
    - API keys (OpenAI, Mathpix): stored in ~/secrets/delta-drills/keys.json
      and the local PostgreSQL users table
    - Auth: admin email + local FastAPI backend (JWT)
    - practiceMode = "backend"

  DEPLOYED (deploy branch, delta-drills.vercel.app)
    - Practice state: Supabase (practice_user_state table)
    - API keys (OpenAI): Supabase user_settings table, loaded on session init
    - Auth: Supabase Auth (non-admin users use Pyodide engine)
    - practiceMode = "supabase" (non-admin) or "backend" (admin on localhost)


THE SUPABASE BOUNDARY FILE
--------------------------
supabase-practice.js is the single file responsible for all Supabase storage.
It lives in BOTH branches with identical content, but its functions are no-ops
when practiceMode != "supabase" or when getSupabaseClient() returns null.

All Supabase storage functions (save/load practice state, save/load user
settings, etc.) belong in supabase-practice.js.


HOW deploy_delta_drills.sh HANDLES THIS
----------------------------------------
The deploy script merges main into deploy with -X theirs (prefer main on
conflict). This would normally overwrite any Supabase-specific additions made
directly in the deploy branch.

To prevent this, the script maintains a DEPLOY_PROTECTED_FILES list at the
top of deploy_delta_drills.sh. Before the merge, it saves those files; after
the merge, it restores them if the merge changed them.

Currently protected:
  - supabase-practice.js


RULES FOR ADDING NEW FEATURES
------------------------------
1. New Supabase storage functions → add to supabase-practice.js in MAIN.
   Use getSupabaseClient() null checks so the function degrades gracefully
   on localhost. Example pattern:

     async function saveXToSupabase(email, data) {
       const sb = getSupabaseClient();
       if (!sb || !email) return false;
       const { error } = await sb.from("table").upsert(...);
       return !error;
     }

2. Shared files (app.js, practice.js, etc.) that call Supabase functions
   should use typeof guards so they work in both modes:

     if (typeof saveXToSupabase === "function") {
       await saveXToSupabase(authEmail, data);
     }

3. If you make a Supabase-specific change DIRECTLY in the deploy branch
   (not recommended), add the modified file to DEPLOY_PROTECTED_FILES in
   deploy_delta_drills.sh so it won't be overwritten on the next deploy.

4. Never put Supabase credentials (service_role key, JWT secret) in any
   frontend file. The anon key in supabase-practice.js is public/safe.
   Backend secrets live in Fly.io secrets only.


ADDING TO DEPLOY_PROTECTED_FILES
---------------------------------
In scripts/deploy_delta_drills.sh, find:

  DEPLOY_PROTECTED_FILES=(
    "supabase-practice.js"
  )

And add the filename:

  DEPLOY_PROTECTED_FILES=(
    "supabase-practice.js"
    "your-new-deploy-only-file.js"
  )

# practice

## Purpose
Practice-page frontend: loads ARENA-derived coding questions, sends the learner
to the Colab notebook each problem was compiled into, and records the result
they report back.

**Practice does not run or grade code, and it does not show the problem.** Since
2026-07-31 there is no editor, no Run button, no output pane, no in-browser
grader — and no prompt, worked example, hint or lesson either. All of that is a
cell in the notebook the problem was compiled into. The learner works it there
and answers one question — *was I able to run the result?* — and that answer
feeds the same mastery chain a graded attempt did.

The reason the CONTENT moved and not just the execution: a worked example is
routinely several code blocks that each build on the state the one above them
left behind. Rendered as static prose in a panel, that is a description of a
program. In the notebook it is the program. The panel keeps what is genuinely
about the session — block setup (question count, per-question answer/review
time), the strict timers, the concept topbar, the competency bar, the two
report buttons and the felt-difficulty rating — plus the one thing that says
where to go: the Colab card.

## Owns
- The practice-page UI lifecycle (init, question selection, self-report, result display).
- Routing the learner to the right Colab notebook and the right cell in it —
  `dd-q<id>` for a problem, `dd-kp-<kc>` for a concept.
- The first-encounter gate: stopping before a new concept and sending the
  learner to the section that teaches it, then recording exposure and crediting
  the ladder's `worked` rung.
- Booting Pyodide, for one reason: the guest/local adaptive engine is Python.
- Adaptive question selection, timing, and progress storage scoped to the practice flow.

## Does NOT own
- Question authoring or curation — lives in `../arena_prereqs_structured.json` and the ARENA source dirs.
- Running the learner's solution. That happens in their Colab notebook, on
  their runtime. The app never sees the code.
- Deciding whether the answer was right — the learner reports that.
- The notebooks themselves, or the `question -> notebook` map. Both are
  generated by `scripts/generate_colab_notebooks.py`, which writes
  `../lessons/colab_notebooks.json` in the same pass as the `.ipynb` files.
- **Showing the problem.** The prompt, its imports, its target image, its
  hints, the concept lesson and the worked example are notebook cells. The panel
  renders none of them, on purpose — a second, inert copy of the thing the
  learner is already reading is worse than no copy.
- Auth, navigation, top-level shell — handled by the host app.

## Key Files
- `init.js`: bootstraps the practice page, wires DOM and event handlers, and
  awaits `ColabRoute.load()` so the first question already has a notebook link.
- `colab-route.js`: **where a problem is worked.** Resolves
  `question -> lesson -> notebook file` through the generated map and builds a
  Colab URL anchored at `#scrollTo=dd-q<id>`, then opens it in ONE reused
  browser tab (`window.open(url, "delta-drills-colab")`). Reusing a named
  window is what makes it work from wherever the learner is, and makes
  consecutive problems in the same notebook a fragment navigation rather than a
  reload. Auto-open is best-effort — browsers only allow it during a user
  gesture — so the visible link is the fallback, not decoration.
- `dom.js`: caches DOM element refs used across modules.
- `lessons.js`: **the first-encounter gate.** When a question's target KC is new,
  renders one card per pending concept into `#lesson-gate` — name, notebook, a
  link to `dd-kp-<kc>` and an "I've read it" button — and steers the shared Colab
  tab there. It does NOT render the lesson. Finishing a card records exposure
  (locally, and server-side in backend mode) and credits the ladder through
  `LadderUI.creditTaught`, which re-stages the pending question before it renders.
- `ladder.js`: the expertise-reversal rungs. Points the concept topbar at the
  current concept and rung, and hands the `worked` rung to `lessons.js`. It no
  longer draws the example beside faded/partial problems: the notebook already
  orders each concept as prose → worked example → that segment's faded problems,
  so the example is a few cells above the problem *and* runnable.
- `events.js`: top-level event handlers (self-report, navigation).
- `engine.js`: loads `practice_engine.py` into Pyodide — the ADAPTIVE ENGINE for
  guest/local mode. Nothing to do with running learner code; it survived the
  teardown for exactly that reason.
- `api.js`: wrapper around `apiFetch` for `/api/practice/*` endpoints, plus
  `recordSelfReport()` — the single place a result becomes a mastery update.
  Backend mode posts `/submit-local-eval` (the same endpoint torch drills already
  used, running the identical BKT/FIRe/decay chain as server-side grading);
  guest mode calls `engine_api.submit_answer` in Pyodide.
- `pyodide-boot.js`: was `runner.js`. Now `initPyodide()` and nothing else. The
  preamble builder, the einops/`numbers.npy` fixtures and
  `runSnippet`/`window.DeltaRunner` went with the lesson cells and the
  target-image preview they served. The interpreter stays because `engine.js`
  needs one.
- `ui.js`: the identity strip (question number, ID chip, calibration badge), the
  Colab card, and the auto-open guard. It renders no question content.
- `ai.js`: post-result AI explanation. The AI *judge* (guest-mode fallback
  grader) was deleted with the rest of the grading path.
- `mode.js`: practice mode (backend vs local-pyodide) selection.
- `adaptive.js`: adaptive question difficulty/selection.
- `questions.js`: client-side question caching/normalization.
- `storage.js`: progress / streak persistence.
- `timer.js`: resumable practice session — learner sets question count + strict answer/review time per question up front (`#practice-session-setup`), then `PracticeSession` enforces them while active. `Pause & exit`, reload, or browser close writes a per-user localStorage snapshot containing the current question, block position, phase, remaining time, and grade review (the editor draft it used to carry went with the editor); setup offers Resume/Discard on return. Answer expiry clicks `#self-report-no` — running out of time IS "was not able to run the result" — or advances when the report row is already gone; review expiry auto-rates the default felt difficulty and advances. Hooks: `onQuestionRendered` (ui.js), `pauseForGrading`/`recordReviewResult`/`resumeAnswerPhase`/`beginReviewPhase` (events.js `_selfReport`), `shouldFinishInsteadOfAdvance` (events.js `_loadNextPracticeQuestion` quota gate). Setup defaults persist in `localStorage.delta_drills_session_setup`; active session key derives from the per-user practice progress key. Styles in `../styles/practice/timer.css`.
- `bars.js`, `bars.css`: progress bars.
- `arena-unlock.js`, `arena-unlock.css`: ARENA UNLOCK INTERSTITIAL — full-viewport overlay that takes over the screen between practice questions when an ARENA exercise crosses its per-subtopic prereq thresholds. Mount point `<div id="arena-unlock-overlay">` lives at body level in `index.html` (not inside `page-practice`) so the takeover escapes any layout/overflow trap. Controller exposes `window.ArenaUnlock.tryShow(onContinue)`; `events.js#nextProblemBtn` calls it before loading the next question and passes `_loadNextPracticeQuestion` as the Continue callback. Reads its data via `window.ARENA_PREREQS_TEMP_*` (defined in `stats/predicted-prereqs-temp.js`); the underlying concept-graph data source is scaffold-only and will be replaced, but this unlock UI is permanent.
- `kc-practice.js`: SINGLE-KC PRACTICE LADDER for the concept graph's "Practice ⤢" overlay (`index.html?lesson=<kc>&embed=1`). Serves the `faded_items` → `guided_items` → `independent_items` lists that `lessons_structured.json` has always carried but nothing consumed. Three rungs of decreasing support: faded hands over a blanked solution, guided hands over the KP's authored hints, independent hands
  over nothing. **The hint delivery changed on 2026-07-31**: the Show-hint
  button it used to ride through is gone with the rest of the in-panel problem
  content. `guided_items`' hints are compiled into the notebook as a `<details>`
  cell directly under the problem, so the learner reveals them where they are
  already working. The `hint` field still travels on the question object, but
  nothing in the panel renders it. Faded items are real bank questions re-served with the KP's blanked starter, so grading/BKT/FIRe run through the normal submit path — this is NOT a parallel scoring system. Scaffold order comes from the learner's posterior using the same ERE band as `arena-unlock.js` (< 0.75 ⇒ faded first). `PracticeAPI.getNextQuestion()` calls `KcPractice.nextQuestion()` while `isActive()`; once the ladder is spent the normal adaptive queue resumes, still pinned by `window.__kcFocusSubtopics`.
- `competency-bar.js`: the mastery bar at the top of that overlay — phase heading (Lesson → Faded drills → Independent problems, driven by the tier actually served, not by the mastery band), a track with both real engine thresholds marked (0.85 unlock, 0.95 mastered), and an rAF tween on each graded attempt. Listens for `competency:feedback-update` (emitted by `events.js`), emits `competency:gate-crossed` + a same-origin `postMessage({type:"delta:kc-mastered"})` that `concept-graph/lesson-graph.js` uses to close the overlay and animate the node. Styles in `../styles/practice/misc.css`.
- `config.js`: feature flags and tunables.

## Data & External Dependencies
- **Question schema**: `arena_prereqs_structured.json` (sibling); per-entry fields include `starter_code`, `canonical_solution`, `runtime_dependencies`, `runtime_unmet_dependencies`, `supports_visual_output`, `expected_artifact_type`.
- **The compiled Colab notebooks** (`arena-book-colab/ARENA_5.0/ch-1-foundations`,
  published from `scripts/`): the only place a learner reads a problem, its
  worked example or its concept. The panel fetches `lessons/colab_notebooks.json`
  to know which notebook and which cell; it never fetches notebook content.
- **ARENA source data**: `../content/ARENA_5.0-main/chapter0_fundamentals/exercises/part0_prereqs/numbers.npy`, `../delta_numbers.npy` (mirrored to Pyodide FS), `../numbers_stacked.png` (static fallback).
- **Pyodide** (CDN): numpy only, for the guest/local adaptive engine.
- **Backend**: `/api/practice/submit-local-eval`, `/api/practice/exposure`,
  `/api/practice/kc-estimate`.
- **Supabase**: progress / streaks via `../supabase-practice.js`.

## How It Works (Flow)
1. `init.js` boots the page; `engine.js` fetches the next question via `api.js`.
2. If the question's target KC is new, `lessons.js` puts up the gate first: one
   card per pending concept, linked to `dd-kp-<kc>`. Continuing records exposure
   and credits the ladder, which re-stages the question before it renders.
3. `ui.js` renders the identity strip — question number, ID, calibration badge,
   concept topbar. It renders NO problem content: prompt, imports, target image,
   hints and worked example are all cells in the notebook.
4. `colab-route.js` steers the single Colab tab to that problem's cell
   (`#scrollTo=dd-q<id>`). The learner reads, writes and runs everything there.
5. **Was not able / Was able to run the result** → `recordSelfReport()`; the
   result feeds `storage.js` and adaptive selection exactly as a grade did.
   Answer-time expiry clicks the *not able* button, so a timeout records a miss
   rather than silently skipping.
6. Solution + felt-difficulty rating, then Next.

## Invariants & Constraints
- **No problem content in the panel, ever.** No prompt, imports, target image,
  hint, concept prose or worked example. They are notebook cells, and a copy
  here is a copy that cannot be run and will drift from the one that can.
  `watch.py:check_lesson_routing` fails if `#question-text`, `#question-imports`,
  `#question-visual`, `#practice-aids` or `#hint-section` reappear in
  `index.html`, or if `ladder.js` starts inserting an example again.
- **Nothing in the gate may depend on an element the practice page lacks.**
  `LessonGate.maybeShow` used to bail on a missing `#code-editor`, so deleting
  the editor turned first-encounter lessons off with no error anywhere — dead
  for four days before anyone noticed. `watch.py` now asserts the gate looks up
  no removed id, and that its exposure + `creditTaught` calls survive.
- **The KP anchor is generated, not derived.** `colab_notebooks.json.kps` ships
  `dd-kp-<slug(kc)>` computed by the Python generator. Do not re-implement
  `slug()` in JavaScript: an anchor that drifts by one character is one Colab
  silently ignores, and the learner lands at the top of a 500-cell notebook
  with no error to explain it.
- **`kps` holds the anchor, `kcs` holds the notebook — one fact per map.** Both
  are keyed by KC. Do not fold the lesson id back into `kps`: it would be the
  same fact written twice, and the copy that went stale would be the one
  nothing checks. `watch.py` asserts the two cover the same concept set.
- **Subtopic naming differs by mode and BKT is keyed by whatever `question.subtopic` says.** Backend `question.subtopic` is composite (`"Numpy: Core array literacy"` — `app/questions.py` prefixes the topic so Numpy/Einops subtopics stay distinct); the local `questions.json` bank uses the bare name and keeps the composite in a separate `subtopic_key` field. Anything matching against a subtopic across both modes must accept EITHER form — that is why `window.__kcFocusSubtopics` is a list and `CompetencyBar.init()` takes an array. `window.__kcFocusSubtopic` (singular) is the composite form only, for the backend's `focus_subtopic` query param.
- **Questions with no lesson-graph KC are PARKED, not served.** `questions.js` builds `kcTaggedIds` from `lessons/qmatrix_tags.json`; `servableQuestions()` / `isKcServable()` back `getPracticeEligibleQuestions()` and `isPracticeQuestionAllowed()`. `questionsBank` itself stays complete so saved/in-flight questions still hydrate — mirror of the backend's complete-by-id / narrowed-pools split. This filter **fails OPEN on purpose**: if the q-matrix can't be fetched nothing is filtered, because an unfiltered offline queue beats an empty one and the backend enforces parking authoritatively for signed-in practice. See `docs/decision-kc-only-serving.md`.
- **No grading in the client, ever.** `recordSelfReport()` takes the learner's
  answer and forwards it; it must never compare anything to a canonical
  solution. A second in-browser grader is a second opinion about what a learner
  knows. `watch.py:check_self_report_loop` fails if `submitAnswer`,
  `fetchAIJudge` or `outputsMatch` reappear in `api.js`.
- **"Was not able" renders LEFT of "was able", and the answer timer clicks it.**
  The timeout default and the negative default are deliberately the same
  control; `watch.py` asserts both the order and the `selfReportNoBtn.click()`
  in `timer.js`. An expiry that advanced without reporting would silently drop
  the attempt.
- **Auto-open only when the problem is on screen.** `openColabForQuestion`
  bails when `#page-practice` is `.hidden` or `.session-idle`. `initPractice`
  renders a question during boot so a session can start instantly, and without
  the guard just loading the app hijacked a browser tab to a notebook for a
  problem nobody had been asked. Asserted in `watch.py`.
- **`lessons/colab_notebooks.json` is generated, never hand-edited.**
  `scripts/generate_colab_notebooks.py` writes it and the extension's
  `notebook-index.js` from one run; `watch.py` fails if the two disagree about
  which notebook a question is in. Editing one by hand sends the learner to the
  wrong cell and nothing else notices.
- `buildPracticeQuestionFromBank()` in `questions.js` is the single bank-record → `currentQuestion` mapping. `api.js` and `kc-practice.js` both use it; do not re-inline it, or a faded item would grade against different fields than the same question served by the queue.

## Extension Points
- **Change what a learner reads for a problem or a concept**: edit the lesson
  source under `../lessons/`, re-run `scripts/generate_colab_notebooks.py`, then
  `scripts/publish_colab_notebooks.sh`. Nothing in this folder renders content.
- **Point at a different notebook repo**: `ColabRoute.setRepo("owner/repo@branch/path")`
  (persisted in `localStorage.delta_drills_colab_repo`); clears back to
  `DEFAULT_REPO` when passed a falsy value.

## Known Issues, Recurring Bugs, and Pain Points (and How to Prevent Them)

- **Run routed torch code to a runtime that has no torch** — `RESOLVED`
  - When it happens: pressing Run on any converted Einops/Einsum drill, or on a torch lesson's worked example, in backend mode.
  - Symptom: `ModuleNotFoundError: No module named 'torch'` from Run, while Submit grades the same code correctly.
  - Root cause: `runner.js` (now `pyodide-boot.js`) forced local Pyodide for lessons ("keep experimentation local") and for `questionNeedsEinops` (which keys on the Einops/Einsum TOPIC, not the library). Both rules predate the torch conversion and silently began covering torch code. Pyodide cannot import torch at all.
  - Prevention/fix: both rules now yield when the question or the snippet imports torch, so it runs on the backend fork runner. Outside backend mode there is no fallback, so Run says so plainly instead of surfacing the import error. When adding a "keep this local" rule, ask what happens to torch code under it.
  - Status: RESOLVED (2026-07-27).
- **Image preview blank when Pyodide errors** — `RESOLVED`
  - When it happens: visual-output question, Pyodide fetch/exec fails.
  - Symptom: empty canvas with only an error string.
  - Root cause: catch block had no fallback path.
  - Prevention/fix: `visuals.js:renderQuestionVisual` called `renderFallbackImage()`
    before showing the error note. Moot since 2026-07-31 — the whole target-image
    preview was removed (it ran the canonical solution in Pyodide, which cannot
    import torch, so it had been degrading to the static PNG for every question
    since the torch conversion). See the visual-question note below.
  - Status: RESOLVED (2026-04-28), code removed (2026-07-31).

- **Torch-dependent prereq questions throw `NameError: 't'`** — `RESOLVED`
  - Root cause: the in-browser preamble injected neither torch nor the ARENA
    test helpers, and Pyodide cannot import torch at all.
  - Prevention/fix: removed by construction (2026-07-31). Nothing runs the
    learner's code in the page — problems are worked in Colab, which has torch.
    The preamble, the runner and `RUNTIME_CONTRACT.md` are gone with it.
  - Status: RESOLVED (2026-07-31).

- **A question with no notebook has nowhere to send you** — `ACTIVE` (contained)
  - When it happens: NOT from the adaptive queue — the KC-tag filter and the
    notebook map cover the same 424 questions, so every question the queue can
    serve is routable. It happens on a **backend placement probe**, which draws
    from the whole 499-question bank including the 75 parked ones.
  - Symptom: no Colab card; the problem is still readable and both result
    buttons still work (the learner may have run it somewhere of their own).
  - Root cause: `colab_notebooks.json` only maps questions the nine compiled
    notebooks actually contain.
  - Prevention/fix: a dead link is worse than no link, so the card stays absent
    — but the **answer timer must not auto-report a miss** for a problem the app
    never gave a way to attempt. `_forceSubmitOrAdvance` checks
    `questionHasColabRoute()` and advances without recording (same contract as
    Skip) when there is no route; `watch.py` asserts that check exists. Do NOT
    make `renderColabCard` invent a URL, and do not drop the timer guard.

- **Popup blocking stops the auto-open** — `ACTIVE`
  - When it happens: the answer timer advances on its own, or the browser
    declines the `window.open` (no transient user activation, or a blocker).
  - Symptom: "Couldn't open the notebook automatically — use the link above."
  - Root cause: `window.open` needs a user gesture; a click has one, an expiring
    countdown does not.
  - Prevention/fix: by design. The visible **Open in Colab ↗** link is the
    fallback and must stay a real anchor — do not replace it with a button that
    only calls `ColabRoute.open`. It must also **never carry
    `rel="noopener"`/`"noreferrer"`**: both imply noopener, and a noopener
    navigation ignores the target NAME and opens a fresh context, so the
    fallback would spawn a new Colab tab on every click. `watch.py` asserts the
    attribute is absent.

- **Visual-target questions lost their reference image** — `ACTIVE` (accepted)
  - When it happens: any of the 26 mapped questions with `supports_visual_output`.
  - Symptom: no "Target Image" preview anywhere. The learner has the prose
    description of the target ("(c, h, w) -> (c, 3h, w): each row appears 3x in
    a row") and nothing rendered.
  - Root cause: the preview worked by running the question's CANONICAL SOLUTION
    in Pyodide and rasterizing the result. Two problems with keeping it: it is
    the question statement, so it belongs in the notebook with the rest of it;
    and it had already stopped working — all 26 are torch dialect since the July
    conversion, Pyodide cannot import torch, so every one had been falling
    through to the static source-data PNG.
  - Prevention/fix: NOT fixed by emitting the render into the notebook. The
    execution plan is built from `expected_expr` / `solution_code`, so a cell
    that draws the target ships the answer in a public repo — exactly what
    `audit_question_bank.py --gate` exists to stop. A real fix needs a target
    image derived from public inputs only, or an authored one. Until then these
    26 rely on their prose.
  - Status: ACTIVE — accepted regression, deliberate.

- **Question gives away answer in starter docstring** — `ACTIVE` (design call)
  - When it happens: function-impl questions where the docstring shows expected output literally (e.g. id 9).
  - Symptom: low cognitive challenge — user can read the answer from the editor.
  - Root cause: ARENA upstream pedagogy embeds expected outputs in docstrings.
  - Prevention/fix: pedagogical trade-off; if changing, scrub docstrings via the export script and verify tests still pass.
  - Status: ACTIVE — keep as-is unless explicitly redesigning.

# practice

## Purpose
Practice-page frontend: loads ARENA-derived coding questions, runs the user's Python in-browser via Pyodide (or via a backend endpoint), grades the result, and renders image previews for visual exercises.

## Owns
- The practice-page UI lifecycle (init, question selection, code editor wiring, run/submit, result display).
- The Pyodide runtime contract and preamble (see `RUNTIME_CONTRACT.md`).
- Image rendering for visual exercises, including the static PNG fallback.
- Adaptive question selection, timing, and progress storage scoped to the practice flow.
- Imported-helper display for practice questions. The UI reads each starter code block and shows the imported names above the editor.

## Does NOT own
- Question authoring or curation — lives in `../arena_prereqs_structured.json` and the ARENA source dirs.
- Backend code execution — handled by the Fly.io backend behind `/api/practice/run-code`.
- AI grading prompts — system prompts live in `../function_mode_quality_*.txt` and `../chatgpt/`.
- Auth, navigation, top-level shell — handled by the host app.

## Key Files
- `init.js`: bootstraps the practice page, wires DOM and event handlers.
- `dom.js`: caches DOM element refs used across modules.
- `events.js`: top-level event handlers (run, submit, navigation).
- `engine.js`: question-selection / submission orchestration; talks to `api.js`.
- `api.js`: wrapper around `apiFetch` for `/api/practice/*` endpoints.
- `feedback-queue.js`: delivery for both feedback surfaces — the reports that
  have not reached the server yet. Loaded BEFORE `api.js`, which calls
  `DDFeedbackQueue` at module scope. 🔴 Split out of `api.js` because every
  defect found in this code has been a lifecycle defect: a drain that
  overwrote what arrived during it, a latch that only covered one tab, a retry
  with no ceiling. The invariants are (a) one drain at a time per queue,
  (b) the write-back re-reads storage and removes only what it delivered,
  (c) 5 rounds of 50 per trigger and no more, (d) an entry is stamped with the
  account that wrote it and is never sent under a different one, (e) every
  report carries a `client_id` so a retry is recognised as the same report.
- `runner.js`: in-browser Pyodide runtime, `buildPyodidePreamble()`, run-button handler. **Runtime contract documented in `RUNTIME_CONTRACT.md`.**
- `question-examples.js`: **the input→output rows under the prompt** (`#question-examples`, a SIBLING of `#question-text` so it survives `LadderUI.decorate`). Two blocks. CORRECT rows are DERIVED from `test_cases[*].call` / `expected_expr` — the same data the grader compares, so they cannot drift from grading and they need no authoring on any of the 535 questions. WRONG rows come from the question's authored `wrong_examples` (`[{call, output, why}]`) and are opt-in: a mutated correct answer is as likely to be a SECOND correct answer, and the `why` is the part that teaches. 🔴 A case's `call` often names a fixture bound in `setup_code`, so a row renders the fixture lines the call reads and THEN the call, REPL-style; the call is shown whole, wrapper and all, because `expected_expr` is the expectation for the whole expression and unwrapping it would pair an input with someone else's output. Nothing here executes and nothing here is graded.
- `visuals.js`: target-image rendering for visual exercises; multi-path `.npy` lookup, canvas rasterization, static PNG fallback.
- `ui.js`: question rendering into the editor and prompt area. Also owns `torchNeedsColab` / `applyTorchRouting` — the binary "notebook card OR editor panel" swap, never both.
- `colab_mode.js`: **which edition this deploy is, and where a question's notebook lives.** `delta-drills-colab.vercel.app` (or `?mode=colab`) is the Colab edition: a drill routes to its published lesson notebook instead of the in-page editor. Both deploys ship IDENTICAL code and ask `location.hostname` who they are, so there is no branch to keep in sync. Exposes `window.DDColab = {active, hrefFor, lessonFor, hrefForKc, lessonForKc, whenReady, openNotebook, revealSolution, framed, debug}`; must load before `ui.js`, which asks it at load time. Inert on the normal app — no fetch, no DOM change. `hrefForKc` is the same join one level up: a CONCEPT resolves through the index's `kcs` / `kps` maps to `#scrollTo=dd-kp-<slug>`, which is what lets the Knowledge Graph route a bubble. Both anchors are shipped by the generator, never re-slugged here — a slug that drifted by one character is an anchor Colab silently ignores.
- `difficulty-dock.js`: **the post-submit interface, frozen to the bottom of the viewport** (`#difficulty-dock`, dressed by `../styles/practice/difficulty-dock.css`). After a grade the Submit button is gone and this is what stands in its place: one question — *"How much harder do you want the next problem to be?"* after a correct answer, *"How much easier…?"* after a miss — with `Slightly / Somewhat / Significantly` under it. 🔴 **It MOVES `#feedback-prompt` and `.feedback-buttons` out of `#practice-feedback-area`; it does not mint copies.** The buttons the learner clicks are the ones `events.js` bound and `ui.js::applyResult` relabels — a forwarding copy would be a second version of a list this folder has already watched drift (see `settleRating` below). 🔴 Because those nodes leave the feedback area, hiding that area no longer hides them, so the dock mirrors **two** classes: `#practice-feedback-area.hidden` (is there a graded result?) and `#page-practice.hidden` (is the learner still on this tab?). It hangs off `<body>`, so without the second one a difficulty question stays pinned to the window on every other tab. Skipped entirely on `html.dd-colab-edition`, whose own sheet already stacks the rating into a column on purpose.
- `basic-mode.js`: **the Advanced-mode predicate** (`window.PracticeBasicMode.active()`), and a gravestone. `../styles/practice/basic-mode.css` hides most of the tab's rails for anyone who has not ticked Advanced mode. 🔴 `active()` is `body.dd-basic-mode` **AND NOT `html.dd-colab-edition`** — the same predicate the sheet states as a selector prefix, and the two must stay identical. 🪦 **`settleRating()` lived here until 2026-08-28.** The sheet used to hide the three rating buttons too, and since that row is both the only backend mutation that moves a subtopic baseline (`POST /api/practice/feedback`; submit and override write `pending_attempt` and stop) and the only thing that revealed Next problem, `settleRating()` clicked the real default button on the learner's behalf — at the cost, stated plainly at the time, of the difficulty signal being `not_much` every time and never the learner's. The rating is not hidden any more (see `difficulty-dock.js`), so the stand-in is gone: answering a visible question for the learner would invent an opinion **and**, now that the same click advances, skip the problem out from under them. `watch_basic_mode.py` still holds the whole contract and returns early the moment the sheet stops hiding `.feedback-btn`; restore both halves together or neither.
- `kernel.js`: **the notebook's live Python session** (`window.DeltaKernel`). Talks to `/api/practice/kernel/{exec,reset}`, where the backend keeps one forked process alive per signed-in learner, so cell 8 sees the `a` that cell 6 bound instead of re-running the whole page. It carries NO cell semantics — the `_delta_cell` harness still lives in `notebook.js` and is sent as `bootstrap`, installed by the server only on a kernel it had to create. Three replies matter to callers: `unavailable` (fall back to `runner.runSnippet`, never shown to the learner), `busy` (409 — the kernel is mid-cell or the box is full; "in a moment", not a failed cell), and `fresh` (the server had no session and made one, so everything the page thought was defined is gone). A 404 latches `unsupported` and turns the kernel off for the page; a network blip must NOT, or one bad moment costs the session.
- `notebook.js`: mounts every runnable fence on a lesson page and owns the cell semantics (last-expression echo, `<cell N>` tracebacks, the bound-name summary, the `In [n]` counter). Runs cells on `kernel.js` when it can and falls back to the stateless `runner.runSnippet` prefix replay when it cannot.
- `notebook-view.js`, `../styles/practice/notebook-view.css`: **the Notebooks tab — a whole compiled lesson on one kernel.** Fetches `../lessons/notebooks/manifest.json`, lists the nine lessons, and renders the one the learner opens: up to 656 cells, every code cell runnable, all of them sharing the single session `kernel.js` keeps on the server. This is the third surface that runs a learner's code (practice page, lesson gate, notebook) and the only one that renders a lesson end to end, so it is deliberately kernel-only: it calls `LessonNotebook.runSource` per cell and NEVER `LessonNotebook.mount`, whose stateless prefix replay would re-run 599 cells to run cell 600. Signed out it still READS, with a banner saying why the Run buttons cannot run. Solutions and hints are compiled in as ordinary cells and are wrapped in `<details>` here — the answer is one click away, never zero. 🔴 Two traps live in this file and are both asserted in `watch_notebook.py`: a cell's source is carried on the node (`_ddSource`), because `innerText` is layout-defined and returns `""` inside a collapsed `<details>` — reading the DOM ran the empty program and reported success; and a run captures the notebook it belongs to (`const state = current`) before its first await, because the learner can press Back or open another lesson while torch is still importing. Deep link: `?notebook=<lesson-id>`.
- `watch_notebook.py`: the checks for the above — load order, the verdict grammar, once-per-visit recording, the carried source, kernel-only execution, closed disclosures, and the assets actually existing on disk.
- `ai.js`: AI-judge submission path.
- `tutor.js`: **the post-answer tutor chat** (`window.PracticeTutor`). A ChatGPT-shaped thread under the AI Explanation in the left panel — tutor turns left, learner turns right, Enter sends and Shift+Enter newlines. `open(ctx)` is called by `events.js` on the same signal that fetches the explanation (a graded attempt in backend/supabase mode), `setExplanation(text)` folds the finished explanation into the context so the tutor does not recite it back, and `reset()` is called by `ui.js` on every question render — one thread per drill, never persisted. The client is stateless: each turn POSTs the whole visible thread plus the problem context to `/api/practice/ai-tutor`, which owns the system prompt. Renders a deliberate three-construct subset of Markdown (fenced blocks, inline backticks, bold) over escaped text rather than pulling in a parser. Styles in `../styles/practice/tutor.css`.
- `mode.js`: practice mode (backend vs local-pyodide) selection.
- `adaptive.js`: adaptive question difficulty/selection.
- `questions.js`: client-side question caching/normalization.
- `storage.js`: progress / streak persistence.
- `timer.js`: the practice session — **one clock per QUESTION, paused and resumed.** 🔴 The allowance is the LEARNER'S again as of 2026-08-28 and it is NOT a constant here: `ANSWER_SECS()` / `REVIEW_SECS()` read `window.SessionClock` on every phase change, so the picker on the idle screen is in force from the next step onward — including **No limit**, which is `null` and means no interval, no expiry and no force-submit at all (`_tick` returns before `setInterval`). Read through the function, never captured: a value taken at load is a clock running under a rule the picker no longer states. `FALLBACK_SECS` (120) applies only if `session-clock.js` failed to load. What the learner still does NOT set is the number of questions or the length of a block; those inputs are still gone. A block has no LENGTH either — `shouldFinishInsteadOfAdvance()` returns `false` forever, and `finish("ended")` and `#session-end-btn` went with the quota they served. Pause and resume are the only two states. Pause (the notch's square, or its menu item) writes a per-user localStorage snapshot — current question, position, phase, remaining time, editor draft, grade review — and puts the readiness screen back; reload and browser close write the same snapshot. 🔴 Snapshot version is **2** and was deliberately NOT bumped for the learner-set clock: a v2 snapshot stores neither `answerSecs`/`reviewSecs` nor `total`, so it resumes on whatever the picker says now — which is the right answer, and a bump would have discarded every paused question on every learner's machine to reach it. v1 snapshots are dropped outright. A paused `remaining` is CLAMPED to the allowance now in force, and `remaining: null` (paused untimed) survives the whole path — `Math.min(null, x)` is 0, which would resume the question already expired. Answer expiry force-submits (or advances when nothing is submittable); review expiry auto-rates the default felt difficulty and advances. Hooks: `onQuestionRendered` (ui.js), `pauseForGrading`/`recordReviewResult`/`resumeAnswerPhase`/`beginReviewPhase` (events.js submit), `shouldFinishInsteadOfAdvance` (events.js `_loadNextPracticeQuestion`). Exposes `idleClockText()` so `notch-menu.js` can show the next question's allowance without holding a second copy of the number. Styles in `../styles/practice/timer.css`.
- `placement-results.js`: **the only writer of the placement results card body** (`window.PlacementResults`). `diagnostic-page.js` decides WHETHER the card shows; this decides what is in it. `/api/practice/diagnostic/status` has always returned `areas[{topic, theta, sd, probes}]` + `atoms_seeded` — nothing rendered them until 2026-08-23, so a learner who had finished the test read "Placement results … will appear here". 🔴 The HEADLINE figure is not computed here any more — it is `readiness.js`'s, drawn in the same `.readiness-dial` the Practice tab uses, with the same caption and detail line (2026-08-23). What stayed is the per-AREA map, which is the one thing the shared figure cannot show: the theta→readiness percentage is a COPY of `app/diagnostic.py::_mastery_from_theta` (`DIFF_FLOOR` 20, `DIFF_SPAN` 80, `SEED_MASTERY_FLOOR` .02, `SEED_MASTERY_CAP` .92) — the same map `finish()` uses to seed per-atom BKT mastery. Drift and the card reports a readiness the rest of the app does not act on; `watch.py::check_the_placement_result_is_the_number_the_backend_seeded` parses both files and compares. 🔴 The backend returns a theta for EVERY area whether or not it was probed (unprobed = the prior, propagated), so `probes === 0` is labelled "not probed" and dimmed, each row carries a ± band from `sd`, and the summary says how many areas were really probed. Rows are weakest-first, and the heading deliberately does NOT promise that is the order practice will follow — `prioritization.py` is weakest-first over SUBTOPICS, weighted and reach-scaled, so it will not match row for row.
- `readiness.js`: **the one "% ready for the ARENA curriculum" in the app.** `window.PracticeReadiness.read()` → `{pct, known, own, mastered, total}` and `.detail(info)` → the sentence under the figure; `session-idle.js` (the Practice idle dial) and `placement-results.js` (the placement results card) are both callers, and neither computes a figure of its own. 🔴 `pct` is the learner's MEAN reading across the 63 concepts in `lessons/kc_registry.json`, not the count past the 0.95 mastery threshold — that count is still reported as `mastered`, but as a completion tally in the detail line. It stopped being the headline because `app/diagnostic.py` seeds a finished placement at `SEED_MASTERY_CAP` 0.92, UNDER the threshold, so the dial read 0% on the same learner the results card had just told "34% ready". 🔴 `own` counts only `source: "atom"` readings — the learner's own evidence about that concept — so a caller can say how much of the mean is measured rather than borrowed from the lesson, the topic or an extrapolation. 🔴 `read()` calls `window.deltaRefreshKcLattice()` itself, once per `opts.stamp`: `kcReadinessInfo` reads lesson-graph.js's OWN `lattice`, which only its `build()` fills, so on Practice and on the placement page every server-side reading fell through to the offline path. The results card passes the placement's `completed_at` as the stamp so the fetch happens once AFTER `finish()` seeded, never per paint. The KC LIST comes from the registry, not from `concept-graph/lesson-graph.js`'s `kcById`: that map is only populated when the Knowledge Graph tab BUILDS, which on the Practice tab never happens, so reading it there answers 0 of 0. Only the per-concept reading is delegated, to `window.deltaKcReadinessInfo`, which is graph-independent. Returns `null` (never 0%) when the registry cannot be fetched — that is a claim about the network, not the learner.
- `session-clock.js`: **how long each question gets** (`window.SessionClock`). Presets — 1:00 / 2:00 / 5:00 / 10:00 / 20:00 / **No limit** — the default (`2m`, what every account was on before), and the per-account stored choice (`<practice storage key>_clock`). Loaded BEFORE `timer.js`, which reads it. 🔴 `secs: null` IS the untimed state; a 99:00 preset is not the same thing, it looks identical for an hour and then submits mid-sentence. 🔴 The placement is not on this clock — every probe keeps `placement-timer.js`'s fixed 2:00, or the test would measure how long each learner chose to sit there.
- `session-idle.js`: **the Practice tab's idle screen** — the readiness dial that replaced "Set up your session", plus the per-question clock picker (`#question-clock-picker`, a radiogroup drawn from `SessionClock.OPTIONS` — this file holds no minutes of its own and calls `PracticeNotch.syncClock()` so the topbar's idle clock follows the choice). Paints `--dd-ready-pct` onto `#readiness-dial` and drives the ONE visible button. 🔴 That button is a PROXY: `#session-resume-btn` and `#session-start-btn` are still the real controls with timer.js's handlers, off the screen but live, and the only decision made here is which to click — from `hasPausedSession()`, timer.js's own answer. It also has to carry the news when a resume is REFUSED (a saved question no longer in the bank): timer.js says so by disabling the resume button and writing the reason into `#session-resume-summary`, both of which are off the screen now, so the label becomes "Start a new question" and the reason is copied into `#session-summary`. Without that the learner presses Continue and watches nothing happen — which is exactly what the first build did. Redraws off a MutationObserver on `#page-practice.session-idle`. Styles in `../styles/practice/readiness.css`.
- `placement-timer.js`: **the placement test's own clock** (`window.PlacementTimer`). The placement runs OUTSIDE a practice session — starting it calls `PracticeSession.finish("placement")` — so none of `timer.js` applies and a probe used to have no limit at all. Every probe now gets the SAME `PLACEMENT_ANSWER_SECS` (120), not a learner setting and not scaled by difficulty: comparable time is what makes the probes comparable evidence. Answer phase only; reviewing a graded probe is untimed. On expiry it submits the learner's own code when they have written any, and otherwise clicks "I don't know yet" (a recorded placement miss with no attempt) — it never invents an answer. The clock is an absolute DEADLINE, never a per-tick decrement: a backgrounded tab gets its interval throttled to seconds or minutes apart, and subtracting one second per late callback quietly handed the learner minutes of extra time. `pageshow` (bfcache restore, which re-runs no script and re-renders no question) and `visibilitychange` settle up against that deadline on return. It is also persisted per question id, so a reload inside the grace window resumes the same clock instead of handing out fresh time. Hooks: `onQuestionRendered` (ui.js, which also STOPS it on any non-probe question), `pauseForGrading`/`resumeAfterFailedSubmit`/`stop` (events.js). Countdown is `#placement-timer`, and it is **on the notch tab** (`.practice-notch-tab`) beside the session clock it takes turns with — Seth, 2026-08-23: "the timer is on the left next to the title thing instead of being on the tab". It has had three homes: `#cold-start-badge`, then `.question-number-row`, now the tab; the constant is that it stays inside `.practice-container`, so it re-parents onto the Placement page with the workspace and there is no second copy to sync. 🔴 It is read BY ID and nothing else — the old `_chip()` minted a `<span>` into whatever row it found when the lookup failed, which is a countdown unstyled by the notch's rules and invisible to `watch.py::check_infotips`; a missing element must mean no clock and a failing watch, not a second one built at runtime. Every show and hide calls `PracticeNotch.syncClock()`, because `notch-menu.js` hides the session clock for exactly as long as this one is visible (the placement runs outside a session, so the session clock would otherwise sit next to it greyed at its idle 02:00). 🔴 No `data-dd-info` any more: the ⓘ is minted as a SIBLING, which in a 15px tab is an icon wedged between the clock and the three dots — key and anchor were deleted together. Styles in `../styles/practice/diagnostic.css`. Invariant: `watch.py::check_every_placement_question_gets_the_same_clock`.
- `bars.js`: **the difficulty numbers, on their way to the ladder's caption.** What is left of the file that drew the two full-width animated tracks — target difficulty and recent accuracy. Both are gone (see the invariant below); the four surviving functions (`setTargetDifficultyInitial`, `setTargetDifficultyFinal`, `setTargetDifficultyUnavailable`, `animateTargetDifficulty`) survive because their call sites in `ui.js` and `events.js` are the places that KNOW the numbers — on render, on submit, on a restored pending answer — and they now forward to `StageLadder.setDifficulty`. `animateTargetDifficulty` no longer animates and no longer applies anything: a line of text has nothing to tween, its `onComplete` fires on the spot so the review flow does not wait for a frame that will not come, and the final reading is applied by that callback alone — applying it here too drew the caption twice per rating and walked past the stale-question guard the Colab path puts around it. `bars.css` is still linked but nothing on this page draws it — `arena-unlock.js` and `targeted-practice.js` build their own bars out of its classes.

- `stage-ladder.js`, `../styles/practice/stage-ladder.css`: **the one progress readout on the practice page** (`#stage-ladder`, a block INSIDE the question's heading card in the left panel — it spanned both panels above the split until 2026-08-23). The concept, then the rung named in words, then the meter — **one** bar cut into four by chevron seams, Lesson · Faded · Worked example · Solo, each named INSIDE its own quarter with a clickable ⓘ beside it — and the reading hanging beneath the bar as a notch pointing up at the fill's edge. 🔴 **The bar draws the whole ladder, not the rung**: `(rungs behind you + progress through the one you are on) / STAGES.length`, said out loud under the fill's leading edge as "38% understanding of concept <name>". It therefore tops out at **75%** on Solo, which is not an off-by-one — `_progress` returns null there (no threshold sits above the top rung) and `kc_is_learned` does not fire on arrival either: it wants the BKT posterior over the concept, or its whole pool served, and neither number is in this payload. Filling the last quarter on arrival would tell the learner they were done with a concept the queue is still going to serve them. It is shared with the lesson screen, which is why it lives above the split and not inside a card. API: `show({kc, title, stage, difficulty, target, support, estimate, eyebrow, integrated})` (a whole screen's worth, replacing everything — the difficulty pair included, so a screen that passes none does not inherit the last question's), `setProgress(estimate)` (a fresh reading after a graded answer — 🔴 moves the FILL and not the rung, because the problem the answer belongs to is still on screen behind it), `setDifficulty(problem, aim)` (from `bars.js`), `setNote(text)` (an extra caption clause; `competency-bar.js` puts the **topic-level** BKT posterior there — 🔴 the caller owes it a scope, see below), `hide()`, `activeKc()`, `normalizeStage()`. 🔴 **`stage` accepts either vocabulary and `STAGE_ALIASES` is the only place they meet** — the backend's `worked` is the LESSON screen and its `partial` is the read-an-example rung; displaying them by their own names once had each rung describing the other one's scaffold. The displayed third rung's id is therefore **`example`**, never `worked`: `worked` already means the lesson screen, and one key with two meanings is a normalizer that has to guess. Its label is still "Worked example". 🔴 **The active section's fill is `max(estimate.ci[0] / PROMOTE_AT[stage], estimate.streak / estimate.streak_needed)`** — `kc_graph._stage_from` has TWO routes out of a rung and takes whichever arrives first, so the bar has to show whichever is further along or it sits at a third while the next correct answer promotes. The run is the half a learner can watch move: the twenty-question window barely shifts on one answer, and on a record carrying old misses it can hold still for a dozen questions. 🔴 **The run is scoped to the rung it was made at, at both ends.** `kc_estimate` counts only a trailing run whose answers were all given at or above the rung the learner now stands on, and sends the rung it counted against as `estimate.stage`; the fill uses the run only while that rung matches the one on screen. Both halves are needed and each fixes a bar that lies in the opposite direction: unscoped, the three answers that promote out of `faded` are still trailing when `partial` arrives, so the new rung draws itself FULL before a single answer is given on it; scoped but unlabelled, the same promotion empties the run while `setProgress` is deliberately still showing the old rung, so the section runs BACKWARDS on the correct answer that finished it. With the rung attached, an estimate from further up means the section on screen is cleared and it draws 100%. Rungs with no threshold (lesson, solo) draw no partial fill rather than inventing one; `watch.py` fails on drift from the backend constants and on the run route going missing at either end. 🔴 **NOTHING IN THIS MODULE MEASURES OR POSITIONS ANYTHING** since the move. The reading was a pop-up whose box was clamped by `getBoundingClientRect` on every render and whose arrow was aimed separately, plus a `resize` listener to redo both; `_renderReading` writes text and that is all. If a floating shape comes back it needs the clamp, the arrow variable, the reserve above the bar and the listener — they were one mechanism and they went together. 🔴 **The concept is named once.** `#question-number` and `#stage-ladder-kc` are both written from `ladder_kc_title`, so inside one card they were the same words twice; the button hides itself when its label would repeat the heading, by READING `#question-number` rather than taking a flag — `show()` has three callers (`ui.js`, `lessons.js`, `concept-graph/lesson-graph.js`) and a flag is a fourth thing to keep in step. The lesson screen sets the heading to "Lesson", so it still names its concept.
  🔴 **`integrated` is NOT a fifth section**, and was one for two days. `ladder_integrated` is a property of the QUESTION — this problem uses the concept beside others already taught — computed at serve time, stored nowhere, and only ever set on a `solo` record; `solo` is the top rung and `kc_is_learned` finishes a concept there. As a dot that lights per question it was fine; as the last section of a track that fills left to right it made Solo read `is-done` and Integrated `is-active` on one problem and both snap back on the next, and showed ground still to cover at the moment the concept was already learned. It is a chip beside the rung name (`#stage-ladder-flag`), passed as its own `integrated` argument, and `watch_lessons.py#check_the_fifth_rung_is_shown_not_stored` holds all of that.

## How It Works (Flow)
1. `init.js` boots the page; `engine.js` fetches the next question via `api.js`.
2. `ui.js` renders prompt + starter code into the Monaco editor.
3. If the question has `supports_visual_output`, `visuals.js` runs the canonical solution in Pyodide and rasterizes the resulting array onto a canvas. On failure, falls back to `numbers_stacked.png`.
4. User clicks Run → `runner.js` either POSTs to the backend or executes locally in Pyodide using the preamble from `buildPyodidePreamble()`.
5. Submit → `ai.js` (AI-judged) or backend grader returns pass/fail; result feeds `storage.js` and adaptive selection.

## Invariants & Constraints
- **`practiceMode === "backend"` is not the same question as "is someone signed in".** Since 2026-08-22 a signed-out visitor is given an account by `../guest-session.js`, so the modes here are reached by guests too — this is what makes the placement diagnostic (`api.js` `diagnosticStart`/`Status`/`Answer`), the lessons (`lessons.js`), the stage ladder (`ladder.js`) and the BKT model work with no sign-in. A new `practiceMode !== "backend"` guard is therefore a statement about the BACKEND being unreachable, never about the learner being anonymous. To ask who the learner is, use `isSignedIn()` in `../app.js`.
- **`initPractice()` must await `window.DDGuest.ensure()` before `detectPracticeMode()`.** The mode is decided once, at init, from whether a token exists; provisioning the guest after that decision would leave every guest in `"local"` mode — the static drill pool, no placement, no lessons — which is the exact failure this replaced.
- The Pyodide preamble in `runner.js` is the **single source of truth** for in-browser injected globals; `RUNTIME_CONTRACT.md` and per-question `runtime_dependencies` must stay in sync.
- Image visuals must degrade gracefully — never leave a blank canvas. Catch path in `visuals.js` must end in either rendered canvas or text note.
- `numbers_stacked.png`, `delta_numbers.npy`, and the ARENA `numbers.npy` source file must remain at served paths; multi-path candidate lookup tolerates moves but `/content/ARENA_5.0-main/...` is the canonical source path for prereq notebook data.
- Never inject runtime globals silently without updating both `RUNTIME_CONTRACT.md` and the JSON probes that derive `runtime_dependencies`.
- AI-judged grading must not rely on `assert_*` helpers being injected — those are not in the in-browser contract.
- **Subtopic naming differs by mode and BKT is keyed by whatever `question.subtopic` says.** Backend `question.subtopic` is composite (`"Numpy: Core array literacy"` — `app/questions.py` prefixes the topic so Numpy/Einops subtopics stay distinct); the local `questions.json` bank uses the bare name and keeps the composite in a separate `subtopic_key` field. Anything matching against a subtopic across both modes must accept EITHER form — that is why `window.__kcFocusSubtopics` is a list and `CompetencyBar.init()` takes an array. `window.__kcFocusSubtopic` (singular) is the composite form only, for the backend's `focus_subtopic` query param.
- **Questions with no lesson-graph KC are PARKED, not served.** `questions.js` builds `kcTaggedIds` from `lessons/qmatrix_tags.json`; `servableQuestions()` / `isKcServable()` back `getPracticeEligibleQuestions()` and `isPracticeQuestionAllowed()`. `questionsBank` itself stays complete so saved/in-flight questions still hydrate — mirror of the backend's complete-by-id / narrowed-pools split. This filter **fails OPEN on purpose**: if the q-matrix can't be fetched nothing is filtered, because an unfiltered offline queue beats an empty one and the backend enforces parking authoritatively for signed-in practice. See `docs/decision-kc-only-serving.md`.
- `buildPracticeQuestionFromBank()` in `questions.js` is the single bank-record → `currentQuestion` mapping. `api.js` and `kc-practice.js` both use it; do not re-inline it, or a faded item would grade against different fields than the same question served by the queue.
- **`recordLocalEval` has two callers with opposite needs, and `finalize` is what separates them.** The Colab verdict IS the whole submit — nothing comes back for it, so it finalizes (the default). The einops fallback in `submitAnswer` is a normal graded submit that merely could not run server-side, so the felt-difficulty step still follows and the attempt must stay PENDING for the rating to attach to: that call site passes **`finalize: false`**. Finalizing there closes the attempt out early and `/feedback` then has nothing to apply, which surfaces to the learner as "Feedback failed" on exactly the einops questions. `watch.py` asserts the flag on every fallback call and its absence on the verdict call.
- **`recordLocalEval` RETURNS what it moved; callers must not re-read globals for it.** Same shape in both modes — `{finalized, targetBefore, targetAfter, pBefore, pAfter}` plus the backend's `ladderStage`/`ladderEstimate` — with `null` for anything there is no honest value for. The offline branch samples the adaptive state before the engine rewrites it; backend mode maps `target_difficulty_before` / `target_difficulty_after` / `p_before` / `p_after` off `/api/practice/submit-local-eval`. Reading `getTargetDifficultyFromAdaptiveState` again after the `await` would report where the state ENDED UP, never where it started.
- **ONE progress readout on the page, and it is `#stage-ladder`.** This screen accumulated four bars: the concept strip's rung dots, a 0-100 difficulty track, an EWMA accuracy track, and the BKT competency track from the graph overlay. Three were on screen at once for a learner who entered through the knowledge graph — reported as "there are THREE different bars in this view" — drawing three quantities that are not comparable in one visual language. They are not three views of a level: **difficulty is the AIM** the queue is pointing at (`20 + 80·Wilson_lower`, an input to selection), **competency is a BKT posterior**, and **accuracy is an EWMA**. Only one of them is now a track, and difficulty is stated as text: "Aiming at difficulty 33.8 · this problem is rated 14", which is the honest version of what the old two-marker bar was implying. `watch.py#check_one_progress_readout` fails if a second mount or a rebuilt track comes back, and `styles/practice/watch.py` fails if any stylesheet in that folder brings the old selectors back.
- **The notebook has two runtimes and the fallback must stay reachable.** On a kernel, a cell is sent alone and state carries; without one, `notebook.js` re-runs cells 1..N to rebuild state before the clicked one. Both paths must produce the same output for the same page, because which one a learner gets depends on being signed in and on whether the backend has a free process — not on anything they did. Guests and older backends keep the replay path forever; do not delete it.
- **A kernel reply's `ok` is the verdict, not its stderr.** A cell that prints a `DeprecationWarning` and succeeds is a PASS, and a cell that calls `sys.exit(1)` silently is a FAILURE — inferring either from whether stderr is empty gets both backwards. Failure with no message at all is its own line (`SILENT_FAILURE`), never "ran successfully".
- **`skipOnFresh` is set for every cell but the first.** If the server had to build the kernel, the client's answer is to replay cells 1..N — and that replay ENDS with the cell that was clicked, so a server that already ran it runs it twice. Anything that appends, writes or counts is not the same cell run twice. Cell 1 does not need it: its prefix IS itself.
- **Add a new injected global**: edit `runner.js:buildPyodidePreamble()`, update `RUNTIME_CONTRACT.md`, re-run the dependency-probe script that populates `runtime_dependencies` in the JSON.
- **Add a new question topic**: extend `questionNeedsEinops` / `questionNeedsArenaArray` in `visuals.js`, ensure the topic's data assets exist in `Local_Deployed_Shared/`, and add probes to the annotator script.
- **Add a per-question fallback image**: set `fallback_image_url` on the question; `visuals.js:getArenaNumbersPngCandidates()` will prefer it.

## Known Issues, Recurring Bugs, and Pain Points (and How to Prevent Them)

- **A lesson page keeps the previous question's difficulty reading** — `RESOLVED`
  - When it happens: navigating from a graded question onto a lesson page.
  - Symptom: the readout says "Aiming at difficulty 40.0" over a page with no
    problem on it and nothing to aim at.
  - Root cause: the readout MERGED what it was given. `show()` only overwrote
    `difficulty` / `target` when the caller supplied them, and the lesson
    screen supplies neither — so the last question's numbers stayed up. The
    2026-08-18 version of this entry called the same bug UNVERIFIED against the
    old `DifficultyBar`; it was real, and reproduced in a browser on
    2026-08-19.
  - Prevention/fix: `show()` REPLACES the pair — both assignments are
    unconditional, `null` when absent. Safe because the practice path
    re-supplies them in the same synchronous render (`ui.js` calls
    `LadderUI.decorate`, then `setTargetDifficultyInitial` fifty lines later),
    and the lesson interstitial runs BEFORE `renderQuestion`, never after.
    `watch.py#check_one_progress_readout` asserts both assignments are
    unconditional — a merge is what this looked like the first time.
  - Status: RESOLVED (2026-08-19).
- **The "support returns" region may not mean support returns** — `ACTIVE`
  - When it happens: target difficulty sits below the 20-point floor.
  - Symptom: the bar's lower zone promises the ladder is about to hand
    scaffolding back, when nothing about the rung has changed.
  - Root cause: `difficulty_offset` (felt difficulty) is added after the
    `20 + 80 * m` formula and is clamped to ±20, so the drawn value can cross
    the floor on offset alone, while an actual demotion is decided by the
    Wilson bound. The label states a consequence the axis cannot guarantee.
  - Prevention/fix: word the zone as where the axis is, the way the upper edge
    already says "pace" rather than "unlocked".
  - Status: `ACTIVE` — cosmetic wording, tracked so it is not rediscovered.
- **Run routed torch code to a runtime that has no torch** — `RESOLVED`
  - When it happens: pressing Run on any converted Einops/Einsum drill, or on a torch lesson's worked example, in backend mode.
  - Symptom: `ModuleNotFoundError: No module named 'torch'` from Run, while Submit grades the same code correctly.
  - Root cause: `runner.js` forced local Pyodide for lessons ("keep experimentation local") and for `questionNeedsEinops` (which keys on the Einops/Einsum TOPIC, not the library). Both rules predate the torch conversion and silently began covering torch code. Pyodide cannot import torch at all.
  - Prevention/fix: both rules now yield when the question or the editor contents import torch, so it runs on the backend fork runner. Outside backend mode there is no fallback, so Run says so plainly instead of surfacing the import error. When adding a "keep this local" rule, ask what happens to torch code under it.
  - Status: RESOLVED (2026-07-27).
- **Image preview blank when Pyodide errors** — `RESOLVED`
  - When it happens: visual-output question, Pyodide fetch/exec fails.
  - Symptom: empty canvas with only an error string.
  - Root cause: catch block had no fallback path.
  - Prevention/fix: `visuals.js:renderQuestionVisual` now calls `renderFallbackImage()` before showing the error note. Keep a static PNG at a served path.
  - Status: RESOLVED (2026-04-28).

- **Torch-dependent prereq questions throw `NameError: 't'`** — `ACTIVE`
  - When it happens: einops-flagged question (forced to local Pyodide by `runner.js:148`) also references `t.tensor`/`Tensor`/`assert_all_*`.
  - Symptom: run output is `NameError`. 18 of 27 prereq questions are affected; see `runtime_unmet_dependencies` per question.
  - Root cause: in-browser preamble does not inject torch or ARENA test helpers; routing forces einops questions to Pyodide regardless.
  - Prevention/fix: route questions with non-empty `runtime_unmet_dependencies` to the backend, OR inject a torch/numpy compat shim in `buildPyodidePreamble`. See `RUNTIME_CONTRACT.md` for the full unmet-dep table.
  - Status: ACTIVE.

- **Question gives away answer in starter docstring** — `ACTIVE` (design call)
  - When it happens: function-impl questions where the docstring shows expected output literally (e.g. id 9).
  - Symptom: low cognitive challenge — user can read the answer from the editor.
  - Root cause: ARENA upstream pedagogy embeds expected outputs in docstrings.
  - Prevention/fix: pedagogical trade-off; if changing, scrub docstrings via the export script and verify tests still pass.
  - Status: ACTIVE — keep as-is unless explicitly redesigning.

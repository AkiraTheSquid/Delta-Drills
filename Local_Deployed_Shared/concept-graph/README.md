# concept-graph/

## Purpose

Front-end assets for **visualising the atom-level concept graph** — the ~205 skills ("atoms") and the prerequisite / encompassing links between them. This folder owns how that graph is *drawn and explored in the browser*; it does not own how the graph is *derived* (that lives in `This-Directory-Only/scripts/` and `This-Directory-Only/backend/`).

## Owns

- The interactive graph embeds shown to users/reviewers.
- The exported, browser-ready graph data (`graph-viz.json`).
- Client-side readiness/prereq helper data consumed by the viz and practice UI.

## Does NOT own

- **Deriving** the graph (edges, tiers, encompassing links) — owned by `This-Directory-Only/scripts/export_graph_viz.py` and the backend `concept_graph.py` / edge-packet pipeline. `graph-viz.json` is a generated artifact; edit the exporter, not the JSON by hand.
- Which problem Practice picks next — that walks the graph but lives in `practice/`.

## Key Files

- **`graph-viz.json`** — exported graph: `{ nodes:[{id,label,topic,family,tier}], edges:[{source,target,enc}] }`. `source → target` means *source is a prerequisite of target*. `enc:true` = encompassing (credit-flow) link; `enc:false` = structural prerequisite. Generated by `export_graph_viz.py`.
- **`graph-viz.js`** — Cytoscape.js embed for the **Knowledge Graph tab** in the main app (`index.html`, `#page-knowledge-graph`). Tiny family-coloured dots, dagre BT layout, tap highlights the closed neighbourhood. Built lazily via `window.deltaInitConceptGraph()` (Cytoscape can't size a `display:none` container). Loads `graph-viz.json` by relative fetch.
- **`graph-audit.html`** — standalone, self-contained **content & structure review** page (justinmath-style). Two-pane: left = clicked skill's detail (label, family/topic/tier, direct prerequisites, unlocks, chain depth — all clickable); right = labeled *bubbles* in a bottom-up prerequisite tree, click lights up the full prerequisite chain in gold. Loads the same `graph-viz.json`. Runs with **no auth/backend** so it can be previewed over a plain static server. Intended as the design prototype for replacing `graph-viz.js`'s dots-only view in the tab.
- **`lesson-graph.js`** — the graph the Knowledge Graph tab actually runs today (supersedes `graph-viz.js`, which is no longer wired into `index.html`). One bubble per KC from `lessons/kc_registry.json`; colour mode toggles between BKT mastery (red→blue) and lesson palette. Clicking a bubble highlights its whole prerequisite chain in gold, renders that KC's lesson content in the left pane, and keeps that node in the **learner-model panel docked across the bottom of the graph pane** (`.kg2-dock`, `is-pinned`): identity + evidence source on the left, P(known) on a bar with a 95% Wilson confidence interval and the 0.85 / 0.95 gate ticks in the middle, and last practised / prerequisites ready / recent accuracy / target difficulty on the right. Hovering any other node previews it in the same panel; mouse-out restores the selected one. "Practice ⤢" opens `index.html?lesson=<kc>&embed=1` in a full-screen iframe.
- **`kc_atom_crosswalk.json`** — generated bridge between the two id spaces (see Invariants). Joins `lessons/qmatrix_tags.json` `target_kcs` with `backend/app/data/question_atom_tags.jsonl` over the 380 questions both tag. Per (kc, atom) pair: `share` = P(atom|kc), `spec` = P(kc|atom), `w = share·spec` renormalized per KC. Per KC: `n`, `reliability` = Σ share·spec, `shared_with` = 1/reliability − 1 (effective sibling KCs drawing on the same evidence), and `tier` — **`measured`** (reliability ≥ 1/3, 20 KCs, safe to read `atom_mastery` per node) or **`topic-proxy`** (44 KCs, atoms coarser than the concept — keep the subtopic fallback). Both cuts are author defaults, flagged in the file. Generated by `This-Directory-Only/scripts/export_kc_atom_crosswalk.py`; never hand-edit.
- **`kc_interval.js`** — owns **how wide the mastery band is**, for every estimate source, and is the only place that decides it. Exposes `window.DeltaKcInterval` in the browser and `module.exports` under node so it can be tested headless. Two pieces: `directEvidenceN({nSub, coveredW, reliability, siblings})` attributes the lesson's graded attempts to one concept (`n_sub × covered_w × specificity`), and `kcInterval({r, nDirect, spreadHalf})` returns the Wilson band at `n_eff = n_direct + n_prior`. `n_prior = ρ²/(1−ρ²) ≈ 0.023` attempts, derived from the ρ ≈ 0.10–0.15 correlation a structural prior has with real performance — see the file header for the derivation. It also enforces the zero-evidence floor.
- **`mastery-bar.js`** — owns **the mastery bar's markup**, and nothing else. Exposes `window.DeltaMasteryBar` in the browser and `module.exports` under node. `render({value, ci, measured, gates, unknownColor})` returns the `.kg2-dock-track` string: fill = the estimate, shaded band = its interval, ticks = the gates. It holds no maths and no styling — the band's width is `kc_interval.js`'s and the `.kg2-dock-*` rules are `styles/how-it-works.css`'s, both untouched by the extraction. **`gates` is opt-in** because 85%/95% are ONE concept's thresholds: the Knowledge Graph dock passes `gates: true`, and an aggregate bar (a Course content section, averaged over its exercises) must not, or it labels a gate that aggregate has no such thing as.
- **`kc_lattice_read.js`** — decides **where a concept's number comes from**, and owns the one case the graph cannot draw its way out of. Order: the server's own row from `/api/practice/kc-lattice` (`tier: measured` and `evidenced`), then the browser's crosswalk read for guests/offline, then null so the caller reaches its labelled fallback. A `topic-proxy` row is refused from either source. `kcLatticeNote(data)` passes the lattice through and, when *every* row is `unmapped`, puts a warning above the graph saying the bubbles are priors — the state production was in from 2026-07-12 to 2026-08-06 with no other symptom.
- **`kc_crosswalk_mastery.js`** — reads a `measured`-tier KC's mastery out of the backend's per-ATOM BKT posteriors via `kc_atom_crosswalk.json`, and reports the `coveredW` behind that read. Topic proxies deliberately return null.
- **`kc_difficulty.json`** — generated per-KC mean question `difficulty_score` (0–100) plus the bank-wide mean, for estimating concepts the learner has never attempted. `target_kcs` only. Generated by `This-Directory-Only/scripts/export_kc_difficulty.py`; never hand-edit.
- **`kc-colab-route.js`** — on the Colab edition, selecting a bubble sends the tab beside the panel to the notebook section that teaches that concept. `lesson-graph.js` calls exactly two functions here — `window.DDGraphColab.onSelect(kc)` / `.onDeselect()` — and knows nothing else about which deploy it is on; the join (kc → lesson notebook → `#scrollTo=dd-kp-<slug>`) belongs to `practice/colab_mode.js`, which reads it out of the generated `lessons/colab_notebooks.json`. It also fills `#kg-colab-link` in the lesson pane, which is the route that still works in a plain browser tab: `openNotebook` is a no-op unframed, because there is no side panel holding the `tabs` permission to steer. Inert on the normal deploy.
- **`atom_readiness.js`**, **`prereq_subtopics.js`** — client-side helpers (readiness scoring / prereq subtopic lookup) keyed by atom id.
- **`iter5_v2.js`** — large iter-5 v2 atom/prereq dataset.

## Data & External Dependencies

- **Cytoscape.js 3.30** + **dagre 0.8** + **cytoscape-dagre 2.5**, loaded from jsdelivr CDN (already trusted by the app). `graph-audit.html` loads them itself; `graph-viz.js` relies on the tags in `index.html`.
- `graph-viz.json` is the single shared data source for both viz surfaces.

## How It Works (Flow)

1. Pipeline exports `graph-viz.json` from the derived concept graph.
2. **Tab view:** app opens Knowledge Graph tab → `deltaInitConceptGraph()` → `graph-viz.js` fetches the JSON, builds a dagre-BT Cytoscape graph, colours by `family`, draws `enc:false` edges red / `enc:true` dashed.
3. **Audit view:** `graph-audit.html` fetches the same JSON, builds `parentsOf`/`childrenOf` from `enc:false` edges only, renders labeled bubbles, and on click BFS-walks `parentsOf` to highlight the full prerequisite chain + populate the left detail pane.

## Invariants & Constraints

- **Edge direction is load-bearing:** `source` is the prerequisite, `target` is the dependent. `rankDir: "BT"` places prerequisites at the bottom. Do not flip without updating both viz files.
- **Only `enc:false` edges form the prerequisite tree / ancestor chain.** `enc:true` edges are display-only (dashed, toggleable) and must be excluded from ancestor/readiness walks.
- `graph-viz.json` is **generated** — never hand-edit; regenerate via the exporter or downstream diffs get clobbered.
- Ancestor walks must be cycle-safe (use a visited set). Current data is a DAG (deepest chain 17) but don't assume acyclicity without the guard.
- Atom ids here are the concept-graph ids; they do **not** map 1:1 to `lessons/` (`kp-*`) or the question bank keys.
- The confidence interval is a **95% Wilson score interval** — Wilson rather than the normal approximation because n is small and p sits near the edges, where the normal interval leaves [0,1] and understates uncertainty. It is honest about *evidence volume*, not about BKT's internal variance (the engine does not expose one).
- **The interval's `n` is per-CONCEPT and must never be a subtopic count.** It used to be `subtopic_states[key].n` — the whole lesson's attempts — for every KC in that lesson, so an untested concept inherited its siblings' evidence and drew a band as tight as a measured one. The `n` is now an *effective sample size*, `n_eff = n_direct + n_prior`, computed in `kc_interval.js`: `n_direct = n_sub × covered_w × specificity`, where `covered_w` is the server's per-KC covered atom weight (from `/api/practice/kc-lattice`, `kc_graph.kc_mastery`) and `specificity` is the crosswalk's `reliability` (falling back to 1/siblings). **`covered_w = 0` forces `n_direct = 0` however large the lesson's pool is** — that term is what makes inheritance impossible.
- **Zero direct evidence is the widest state on the map.** Enforced, not hoped for: `kcInterval` floors the half-width of anything below one attempt's worth of direct evidence at `ONE_ATTEMPT_HALF` = Wilson(p=0.5, n=1) ≈ 0.445. **Invariant: a KC with zero direct evidence never draws a band narrower than a KC with one real graded attempt.** (The algebra already holds for any `n_prior < 0.47`; the clamp is there so retuning `PRIOR_R` cannot silently break it.)
- **A prior is not a measurement, and its width must say so.** Subtopic inheritance and the difficulty-shifted extrapolation are both structural priors of the same kind, correlating with real performance at ρ ≈ 0.10–0.15, so both are worth the same ≈ 0.023 effective attempts and both draw a near-full-width band. Keep them — a blank map was the wrong default and the point estimate is genuinely useful — but never let either size the band like observation. What distinguishes them is only *where the number came from*, which the dock states in words.
- **Anything below one attempt's worth of direct evidence is drawn as inferred**, not just the extrapolated ones: washed-out and dashed on the graph, `is-inferred` hatch on the dock band, and a readout that says "No direct evidence — inferred from related work" instead of a `95% CI` line. Keying that on `source === "extrapolated"` (the old test) let the far commoner subtopic-inherited case look solid.
- The dock's height is a single source of truth: `--kg2-dock-h` on `.kg2-graph` sets the panel height **and** insets `#kg-cy`, so the canvas never sits under the panel. The panel is always mounted (empty state when nothing is selected) so hovering bubble to bubble cannot reflow the canvas under the cursor. `fitWrap()` sizes `.kg2-wrap` to the space actually left below the app chrome — the CSS `calc(100vh - 92px)` assumes a banner that isn't always there, and any overhang would push the dock below the fold.
- The panel must keep concept-level and subtopic-level numbers **visually separate and separately labelled**. They are different measurements: `atom_mastery` is per-KC and today only the backend writes it, while `subtopic_states` is what the practice queue actually runs on and is shared by every KC in the lesson. Collapsing them into one "your mastery" figure would assert per-concept precision the offline engine does not have.
- A subtopic is stored under two names — bare (`Core array literacy`, offline bank) and topic-prefixed (`Numpy: Core array literacy`, backend). Any lookup keyed by subtopic must try both; see `practice/README.md`.
- **The bubbles' KC ids and the backend's BKT atom ids are disjoint id spaces.** The graph draws the 64 KCs of `lessons/kc_registry.json` (`numpy.dtype-astype`); `atom_mastery` is keyed by the concept-graph atoms of `backend/app/data/question_atom_tags.jsonl` (`argmax-prediction`). Measured overlap: **zero**. So `kcReadinessInfo()` falls back to the lesson subtopic's correctness rate `p` (requires `n > 0`; `p` defaults to 0.5 and an unpractised concept must stay grey) and reports `source: "subtopic"`, which the panel labels *lesson-level*. Any caller that shows this number must say which layer it came from — a lesson number is not a per-concept measurement. A true per-concept estimate needs a KC→atom crosswalk; **`kc_atom_crosswalk.json` now builds one** — but it rescues only 20 of the 64 KCs, so the subtopic fallback stays the default path for the other 44. See the crosswalk's own entry under Key Files.
- **The crosswalk does not license reading `atom_mastery` for every KC.** The join is many-to-few — 64 KCs onto 56 atoms, with `einops-einsum` tagged across 12 KCs and `broadcasting-rules` across 14 — so for most `einsum.*` / `einops.*` KCs the atom is *coarser than the concept*. Reading it per KC would hand ten sibling nodes one identical number and present a topic average as a per-node measurement, which is exactly what the invariant above forbids. Only KCs with `tier == "measured"` (reliability ≥ 1/3) may be read this way; `tier == "topic-proxy"` KCs must keep the subtopic fallback and its *lesson-level* label.
- **Bare subtopic names are not unique.** `Core array literacy` and `Applied patterns and advanced` each exist under both Numpy and Einsum, and the backend strips the topic prefix before sending state (`subtopic_router._unprefix_subtopic`), so those pairs arrive collided under one key. The panel names the merge (`· merged across Einsum + Numpy`) instead of presenting it as one lesson's own evidence. The underlying collision is server-side and still open.

## Extension Points

- To change the tab's look, edit `graph-viz.js` (or port `graph-audit.html` into it once its style is approved).
- New per-node fields: add them in the exporter → they appear in `graph-viz.json` → surface in the `data(...)` mappers / info panel.
- To show real per-skill content (drill/lesson) in the audit pane, first establish an atom-id → question/lesson mapping (none exists today).
